Eclipse Architecture & Schema

Working architecture document • 2026-08-15 • conceptual/UX schema, not a locked implementation specification
Guiding concept — Pseudo-cognition: convert media-derived observable behavior, social responses, context, and relationships into editable nodes that can support fictional simulation and, conceptually, narrative decomposition and recomposition.
Terminology migration: “Relationship Variant” is the former convergence behavior represented inside a Relationship Node. There is no standalone Convergence Node. This older conceptual document is retained as background; see Documentation_Migration_and_Authority.md for current decisions.

1. Scope and status

This document records the architecture and schema discussed during the Eclipse UX/UI iterations. It is intentionally a working conceptual schema. The final technical foundation, exact node taxonomy, and exact node count remain open decisions.

The immediate goal is to make the UX/UI authoring model coherent enough that another AI can build the interface correctly. Implementation details can be formalized later after the accumulated HTML design documents are consolidated.

2. Core idea

CHARACTER BRAIN
      |
      +-----------------------------+
      |                             |
DIRECT / CHARACTER DATA      SUPPORT / REFERENCE DATA
      |                             |
      +-------------+---------------+
                    |
                    v
            COMPUTED COGNITION
                    |
          +---------+---------+
          |         |         |
       BEHAVIOR   DIALOGUE  REACTION
                    |
                    v
                  LLM

The system is intended to function as an active cognition layer for fictional characters, rather than merely a prompt library or character-description database. Evidence describes what was observed; relationships, RELATIONSHIP VARIANT, rules, weights, priorities, biases, and overrides control how that evidence interacts.

Critical UX interpretation: the large Group Node is a giant first-class graph node, not a passive background container. The group contains a nested graph and exposes an aggregate/output boundary to the external relationship graph.

4. Group Node

Purpose

A Group Node represents a large graph object containing related Character Nodes and their internal structures.

Conceptual fields

{
  id,
  type: "group",
  name,
  children: [characterNodeId...],
  group_rules: [],
  group_priority,
  group_overrides: [],
  output_signal
}

The exact number of group subtypes is intentionally not fixed.

5. Character Node

Purpose

A Character Node represents a character-specific graph inside a Group. The node visually carries a character image/representation and exposes an internal graph.

{
  id,
  type: "character",
  character_id,
  representation,
  image,
  persona_state,
  children: [internalNodeId...],
  hidden_sublevels: [sublevelId...],
  internal_relationships: [relationshipId...]
}
The image is not merely decoration. It identifies the character/representation associated with that graph segment, especially when multiple persona or state representations are present.

6. Internal Data Nodes

An internal data node represents a particular evidence/data dimension inside a character graph. The final taxonomy is still open.

Transcript Image Audio Video Analysis Social / Cultural Reference Character Reference Relationship Evidence General Writing Reference 
{
  id,
  type: "evidence",
  data_type,
  source,
  target,
  scope,
  global_weight,
  priority,
  confidence,
  evidence,
  extracted_signals,
  node_rules: [],
  node_biases: [],
  node_overrides: []
}

7. Hidden Sublevels

A Character Node may expose a hidden sublevel containing deeper topology. This is not simply a hidden text field; it is an expandable graph layer.

Character Node
   |
   +-- visible data
   |
   +-- [Hidden Sublevel]
           |
           +-- deeper Data Nodes
           +-- Sub-Relationships
           +-- state-specific nodes
           +-- additional graph structure

8. Internal graph aggregation

[Data Node] ──┐
[Data Node] ──┼──→ internal graph ──→ Group Output
[Data Node] ──┤
[Relationship]┘

For the UX, the Group Output/Data Bus is a clear aggregation boundary. It is currently safest to treat that as a visual/interaction mechanism rather than permanently defining it as a separate semantic node until the technical foundation is finalized.

9. Relationship Node

A Relationship Node represents an actual story/character relationship and is distinct from a RELATIONSHIP VARIANT.

{
  id,
  type: "relationship",
  source_character,
  target_character,
  relationship_type,
  relationship_strength,
  scene_conditions,
  behavior_rules: [],
  priorities: {},
  persona_weights: {},
  biases: [],
  overrides: []
}
Do not collapse Relationship and RELATIONSHIP VARIANT. A Relationship means the characters/datasets participate in an actual story relationship. A RELATIONSHIP VARIANT means evidence sources overlap on a behavioral dimension.

10. RELATIONSHIP VARIANT

{
  id,
  type: "RELATIONSHIP VARIANT",
  source_node_ids: [],
  shared_dimensions: [],
  similarity,
  contrast,
  transfer_weights: {},
  confidence,
  priority,
  filters: [],
  rules: [],
  biases: [],
  overrides: [],
  selective_transfer: {}
}

Selective transfer allows a reference dataset to contribute only chosen dimensions, such as comedy, dialogue, social reaction, visual design, or other explicitly allowed signals, rather than becoming a personality transplant.

11. Relationship state and persona priority

NORMAL MODE
Sally     70%
Fujiko    30%

TRANSFORMATION MODE
Sally    100%
Fujiko     0%

HYBRID MODE
Sally     50%
Fujiko    50%

The relationship layer needs to be able to hold mode-dependent state and priority. The exact UI controls can evolve, but the concept should remain accessible from the relationship inspector.

12. Rules, biases, priorities, overrides

GLOBAL
  ↓
GROUP
  ↓
CHARACTER
  ↓
INTERNAL NODE
  ↓
CONNECTION / RELATIONSHIP
  ↓
ACTIVE STATE OVERRIDE

Controls should remain hierarchical rather than being flattened into a single giant prompt. Connection rules may have different authority from ordinary evidence. Overrides can take precedence when the story explicitly requires a transformation, temporary condition, scene-specific behavior, or other deliberate exception.

13. Computation model

RAW DATA
  ↓
EXTRACTION
  ├─ dialogue signals
  ├─ reaction signals
  ├─ visual signals
  ├─ audio signals
  └─ interaction signals
  ↓
EVIDENCE NORMALIZATION
  ↓
NODE WEIGHTING
  ↓
RELATIONSHIP VARIANT / RELATIONSHIP RESOLUTION
  ↓
PRIORITY / BIAS / OVERRIDE RESOLUTION
  ↓
ACTIVE CHARACTER STATE
  ↓
LLM GENERATION

The visual animation of data moving through the graph should communicate this pipeline when the author runs/updates computation.

14. Active Cognition

{
  character,
  persona_state,
  relationship_state,
  current_mode,
  active_experience,
  behavioral_signals,
  confidence,
  resolved_rules,
  final_behavior_signal
}

This is the bridge between graph authoring and generation. The graph is not the final story. It is the structured state resolver that produces what should be true for the character in the current context.

15. Board interaction contract

InteractionRequired behavior
SelectSelect node or connection and expose inspector.
MoveMove groups, character nodes, relationships and author-created nodes.
ConnectDrag from a connection dot to another compatible dot.
DisconnectSelect edge and delete/disconnect without deleting nodes.
Expand / CollapseExpand groups, characters and hidden sublevels.
Pan / ZoomNavigate a large whiteboard.
Fit BoardFit authored graph to the viewport without making it unreadably small.
Undo / RedoRestore graph edits and node layout.
DuplicateCopy a node while preserving reusable structure and allowing retargeting.
Disable EdgeTemporarily suppress a connection without deleting it.

16. UI responsibilities

Whiteboard

Show topology, hierarchy, relationships and data flow.

Node

Show identity and the minimum information needed to understand what it is.

Connection

Show how information/relationship/state moves through the graph.

Inspector

Hold detailed weights, confidence, rules, biases, priorities, overrides, filters and state controls.

17. Style direction

Use the existing V2 and V3 HTML prototypes as visual references. V2 is the stronger reference for the polished Eclipse shell, inspector, navigation and board presentation. V3 is the stronger reference for the nested Group → Character → Hidden Sublevel → internal graph topology. The Sally/Mallory mockups are visual reference material for relationship-oriented authoring.

Important: style references are references, not implementation constraints. Preserve the architecture and interaction language while improving visual quality.
