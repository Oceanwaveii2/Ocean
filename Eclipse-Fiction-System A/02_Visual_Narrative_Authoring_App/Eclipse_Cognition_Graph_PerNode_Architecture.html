Eclipse Cognition Graph

Per-node evidence, RELATIONSHIP VARIANT, relationship logic, weighting, priorities, biases, overrides, and copyable datasets for a visual fiction-engine authoring system.

Guiding concept — Pseudo-cognition: convert media-derived observable behavior, social responses, context, and relationships into editable nodes that can support fictional simulation and, conceptually, narrative decomposition and recomposition.

Migration status: “Relationship Variant” is an internal variant of a Relationship Node, not a standalone node type. This is a conceptual background document; current decisions are in Documentation_Migration_and_Authority.md.

1. Core Design Principle

The system is intended to function as an active cognition layer for fictional characters. It is not simply a prompt library and not simply a database of character descriptions. The goal is to organize evidence so an AI can compute how a character should behave, react, speak, interpret a situation, and interact with other characters.

Central separation: Evidence describes what was observed. Relationship and RELATIONSHIP VARIANTs describe how evidence is allowed to interact. Rules, weights, priorities, biases, and overrides control that interaction.

The UI should stay simple. The author creates an evidence node, selects the data type from a dropdown, identifies the source and target, and sets its global influence. The deeper schema remains inside the inspector rather than cluttering the board.

Supported data types

The data type describes the medium or evidence format. The target/source identity describes what the evidence is about. Those concepts should not be collapsed.

3. Direct Character Dataset vs Reference Dataset

A transcript can contain many characters, but the engine must know which character is being mined. This prevents a large episode from accidentally turning every character in the episode into one personality.

Direct Character Dataset

The evidence is intended to model the target character directly.

Type: Transcript
Source: Magic User's Club
Target: Akane Akawa
Scope: Direct
Weight: 90
Priority: High
Reference / Supporting Dataset

The evidence fills a behavioral gap or supplies a comparative signal. It does not redefine the target character.

Type: Transcript
Source: Love Hina
Target: Naru Narusegawa
Scope: Reference
Weight: 55
Purpose: Comedy / reactions
Important: supporting data must never silently become identity data. If a reference character is useful because of a particular trait, only that selected behavioral dimension should be eligible for transfer.

4. Global Weight

Every dataset gets a global weight. This determines how strongly that dataset contributes to the character's overall evidence hierarchy. 

PRIMARY CHARACTER EVIDENCE
Akane direct data ................ 90
        |
        +---- strongest authority

SECONDARY REFERENCE
Naru comparative data ............ 55
        |
        +---- useful for selected gaps

TERTIARY REFERENCE
Other material ................... 20
        |
        +---- weak contextual signal

A weight does not mean "this character becomes the reference character." It means "this evidence source has this much authority when the engine is computing the relevant signal."

6. Relationship Node vs RELATIONSHIP VARIANT

Relationship Node Represents an actual story relationship between characters. Akane ↔ Taro Rivalry, friendship, affection, family, conflict, dependency, etc.
RELATIONSHIP VARIANT Connects evidence sources because they overlap on a behavioral dimension. Akane ↔ Naru Both provide useful evidence about expressive comedy or social reactivity.

            |

This distinction is crucial. Otherwise the graph becomes a spaghetti bowl where "these characters remind me of each other" accidentally becomes "these characters know each other."

8. Sparse Character Problem

Minor characters are inherently difficult to reproduce because the available evidence may only consist of a handful of scenes. The engine should represent that uncertainty rather than hallucinating a complete personality.

A reference dataset can fill a missing behavioral dimension, but its lower weight and scope restrictions prevent it from pretending to be original canon evidence.

9. Mixed Data Volume and Structure

Different sources produce different kinds and quantities of evidence. A long transcript, a single image, an influencer-style post, an audio recording, and a character capture should not be treated as equal simply because each is "one dataset."

EvidencePossible informationTypical limitation
TranscriptDialogue, reactions, jokes, interactions, recurring behaviorMay miss visual/audio cues
ImageAppearance, pose, expression, visual motifsVery little temporal behavior
AudioTone, cadence, rhythm, emotional energy, deliveryMay lack visual context
Video analysisCombined behavior, timing, gesture, scene dynamicsMore expensive to process
Social / cultural referenceSpeech patterns, attitudes, aesthetics, behavioral signalsMay not represent a fictional character

The engine should therefore track both weight and evidence quality/confidence. A dataset with thousands of weak or irrelevant samples should not automatically defeat a small, high-confidence direct dataset.

10. Selective Transfer

The most important safeguard for reference data is dimensional transfer. A RELATIONSHIP VARIANT should be able to specify what is allowed to cross the connection. 

REFERENCE DATASET
       |
       v
+--------------------------+
| SELECTIVE TRANSFER       |
|                          |
| Comedy .......... 85     |  <-- allowed
| Dialogue ........ 70     |  <-- allowed
| Social reaction . 60     |  <-- allowed
| Visual design ... 15     |  <-- weak
| Biography ....... BLOCK  |  <-- never transfer
| Canon history ... BLOCK  |  <-- never transfer
+--------------------------+
       |
       v
TARGET CHARACTER

This lets a reference character act as a behavioral tool without becoming a personality transplant.

12. Rules, Biases, Priorities, and Overrides

Each node and each connection can have its own control layer. The controls should be hierarchical rather than flattened into one giant global prompt.

An override should have higher authority than ordinary evidence when the story explicitly requires it. This is especially useful for transformation states, temporary character conditions, scene-specific behavior, or other deliberate exceptions.

  • Draw connections between nodes.

17. Why This Architecture Fits the Fiction Engine

The original fiction-engine problem was that an ordinary LLM tends to flatten a character into a handful of obvious adjectives. It can also overuse the strongest or most recent piece of context. The graph provides persistent structure.

Without the graph

Prompt → LLM → generic personality → story.

With the graph

Evidence → weighted cognition → relationships/RELATIONSHIP VARIANTs → active state → LLM → story.

This makes it possible to keep low-frequency information alive. A small recurring behavior does not have to disappear simply because the current scene is about something else. Likewise, a huge reference dataset does not automatically overwhelm a smaller but more authoritative character dataset.

18. Design Rules to Preserve

  1. Evidence and inference are different. Store what was observed separately from what the engine concludes.
  2. Direct character data has higher authority than reference data.
  3. Global weight controls overall influence.
  4. Connection weights control influence between specific datasets.
  5. Reference data must be dimension-filtered.
  6. Relationship nodes and RELATIONSHIP VARIANTs are different concepts.
  7. Overrides outrank ordinary evidence when explicitly configured.
  8. Sparse characters should carry uncertainty rather than fabricated completeness.
  9. Large datasets should not automatically overpower small, high-quality datasets.
  10. Nodes should be copyable and reusable.
  11. The whiteboard is the primary visual authoring surface.
  12. Complex controls belong in the inspector, not on every node.

20. Implementation Direction

The first implementation should remain deliberately small. A working prototype does not need a neural network or an elaborate knowledge graph. It can use JSON objects representing nodes and edges, then perform deterministic weighting and filtering before handing the resolved context to an LLM.

The result is a system where the author can literally see the character's cognitive architecture on a whiteboard, move evidence around, connect datasets, tune relationships, and then run the graph as a structured pre-processing layer for story generation.
